# I1 — Plugin-only feasibility gate for the **existing M3 Bluetooth controller**

**Owner scope lock, 2026-11-02.** This is the current target of **Draft PR #52**. Decide whether an actual *removable, maintainable plugin* can add genuine DS3 wireless support to the **already-working built-in M3 radio**, without replacing OEM `libbluetooth.so` or rebuilding the Android BSP. Do **not** change the goal to a USB dongle, an independent second radio, a new native Fluoride build, a source patch, or a full Android stack rebuild. The previous userspace USB HCI / kernel config material is **deferred research** for a **separate future PR**; no dongle PR is opened now. Historic research commits are retained, not asserted as the current solution.

## The question to prove or falsify

A **supported plugin route** must give a separately installable component a *real* registration/load contract, not just a shared-library name. To be viable for the DS3, that contract must also give enough **authorized, per-device** control to address all three independent failure boundaries:

1. **Native HCI/BTM authentication and Classic HID L2CAP**: real legacy pairing behavior and peer verification, avoiding historic Authentication Complete status `0x22`, without forged bonds/LinkKeys, insecure global policy, or stealing the controller.
2. **Java HID Host admission**: `BOND_BONDED` / policy and possible virtual-unplug in the OEM `HidHostService`; notification or UI-only plugins cannot override a native admission gate.
3. **HID/UHID transactions**: accurate report/SET_REPORT replies and Android input for RetroArch **after** a legitimate Bluetooth session, not mock or spoofed input.

A DLL-like `.so` existing in a directory, exported symbols, `dlopen`, Binder observation, a root shell, a HID Device profile, or a kernel module **alone** does not meet this definition.

## What must be checked next — **OEM-specific**, offline and plugin-only

**P1 — Prove the exact M3 OEM dynamic-library load surface.** From an *already obtained* Owner-controlled original M3 system image / Bluetooth binaries (never commit binaries), inspect the byte-identical original `libbluetooth.so`, Bluetooth app JNI and actual vendor/HAL libraries. Record sanitized hashes/build IDs, `DT_NEEDED`, `SONAME`, **actual `dlopen` / `android_dlopen_ext` / `dlsym` callsites**, targeted static strings, link namespaces and load paths. Do not call a `DT_NEEDED` dependency a plugin. Record both positive findings and bounded negative search coverage. Keep SHA/build evidence without raw private binary.

**P2 — Verify every real candidate's ABI contract.** For each discovered load path, seek name/config/registration symbol, callback signatures, invocation phase, supported version, multiple listeners or exclusive owner, permissions and cleanup. Explicitly connect it to **BTM security, HID PSM 0x11/0x13, JNI/Java admission, UHID SET_REPORT**. A loadable `.so` with **no access to the required lifecycle gates is NO_GO**.

**P3 — Look for a supported *external* Bluetooth profile/service API.** Pinned Android Java `Config` enumerates known built-in services; inspect the **OEM APK/DEX** for private dynamic profile resolution or vendor extension, and available proprietary interface documentation. Hidden/privileged API access, registration inside the Bluetooth system app, or replacement of the APK does not automatically count as an installable plugin. Existing profile setters or PIN UI cannot turn `0x22` into a genuine authenticated DS3 session.

**P4 — Explicit falsification / result.**
- **PLUGIN GO (source/interface only):** a *verified* real OEM-supported, removable loader/IPC endpoint + versioned callback contract + legitimate per-device native/Java/UHID control and safe controller ownership, with no global authentication relaxation. Only then design smallest offline interface prototype.
- **PLUGIN NO_GO for inspected OEM version:** exact OEM load/registration and service interfaces inspected, no supported entry point can handle required native security/Java admission while preserving OEM operation. State search completeness, unknown stripped code, vendor undocumented APIs and limits; do **not** claim mathematical impossibility.
- **UNRESOLVED:** OEM bytes/interface documentation unavailable or candidate not tested; no speculative injection or second-controller switch. Ask Owner to choose whether to supply more evidence or stop; do not silently divert PR #52.

## Important Android broadcast caveat (do not claim manifest-only background support)

Official Android [BluetoothDevice API documentation](https://developer.android.com/reference/android/bluetooth/BluetoothDevice) confirms `ACTION_PAIRING_REQUEST` and `setPin(byte[])`, including Bluetooth permission requirements for Android 12. The [Android implicit broadcast exemption list](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions) lists certain ACL-connected/disconnected and other Bluetooth broadcasts but **does not list `ACTION_PAIRING_REQUEST`**. Android's [broadcast receiver guidance](https://developer.android.com/develop/background-work/background-tasks/broadcasts) says most manifest-declared implicit receivers targeting 26+ are restricted. This is a **deployment feasibility caveat, not a proof that Android never delivers pairing requests**; actual M3 OEM broadcast routing is untested. A dynamically registered receiver in an already-running app would avoid the manifest-only assumption but has its own persistence/foreground/boot limits.

**No PIN bytes or implementation are provided**: DS3's recognized USB cable enrollment is not itself a classic Bluetooth LinkKey. Previously captured `HCI Authentication Complete` event `0x06` status **`0x22 = LMP Response Timeout`** and **four missing host PIN command windows** do not prove a normal user-entered PIN is the correct handshake. See [specific HCI/BlueZ comparison](M3-DS3-I2-HCI-0X22-BLUEZ-CABLE-PAIRING-VS-PLUGIN.md).

## Updated P1/P2/P3 decisions for PR #52

**Public H618 Android 12 plugin surface:** **NO_GO for a standalone *complete DS3 compatibility plugin* via the inspected standard APK/HID/JNI/BTIF interfaces.** The supported pairing receiver is **CONDITIONAL for one narrow PIN handoff only**, and Binder `HidHostService` operations require stronger permissions. Native HID callbacks have **one owner**, Java profile classes are pre-enumerated, and actual Classic HID auth + Java bond + UHID need internal control.

**Actual M3 OEM proprietary extension:** **UNRESOLVED**. The previously uploaded exact-2024 ELF, APK and JNI Library records were found, but no raw bytes could be materialized into this session; no new exact-OEM disassembly/import/loader callsite inspection occurred. S7 child `dlopen` experiments are **not** evidence of a supported OEM plugin contract. Require actual OEM loader/registry API (path, callback ABI, ACL/security/hid scope, permission, lifecycle/recovery), or document a bounded **OEM NO_GO**, not impossibility in all conceivable systems.

**Next concrete, source-correct work:** maintain an OEM-specific *positive extension candidate register* (library/binder/manifest evidence with provenance) and only develop an offline plugin interface prototype if an actual supported extension reaches native security + Java bond + UHID. Do **not** retrofit source patches from PR #51 or BlueZ security weakening into this PR. No new device operation, no system changes, and no USB Bluetooth dongle/USB-HCI work.

**CI limitations:** The successful pinned source gate and 8 synthetic tests validate source identity and predicates; they do **not** demonstrate Android runtime delivery, loader support in real M3, a working wireless DS3, or a complete extension interface.


## Archived **actual M3 OEM package-manager dump** strengthens the pairing admission finding

**Evidence provenance:** Owner's previously uploaded `m3-tv-settings-package.txt` and `m3-bluetooth-package.txt`, originally collected from the M3 and still readable as indexed Library *text* in the current research session. These are **original installed package-manager snapshots**, **not** live operation or freshly hashed ELF/APK. The full dumps contain system details and **are not added to GitHub**. The following is sanitized, limited to package/class names and granted permission flags.

- **Actual M3 TV Settings** `com.android.tv.settings`, **Activity Resolver Table** has action `android.bluetooth.device.action.PAIRING_REQUEST` mapping to **`.bluetooth.BluetoothPairingDialog`** (UI Activity). Separately, **Receiver Resolver Table** maps the same broadcast action to **`.bluetooth.BluetoothPairingRequest`** (BroadcastReceiver). These are *two different Android components*; do not conflate the Activity with the broadcast receiver. Existing OEM Android logcat from a separate capture shows `BluetoothPairingRequest: onPair: null`.
- The M3 TV Settings package is an installed **SYSTEM / PRIVILEGED / SYSTEM_EXT** app and the archived requested/granted permission list marks **`android.permission.BLUETOOTH_PRIVILEGED: granted=true`**, and runtime permissions mark **`android.permission.BLUETOOTH_CONNECT: granted=true`**. Therefore **this is not a normal permission-only third-party receiver**; Android may treat delivery/privilege differently for it.
- The actual installed `com.android.bluetooth` package resolves **`.hid.HidHostService`** for `android.bluetooth.IBluetoothHidHost` and `.hid.HidDeviceService` for `android.bluetooth.IBluetoothHidDevice`. These are distinct profiles. The former is host-side DS3 functionality; the latter does not furnish a host plugin.
- These package snapshots **do not prove** receiver intent-filter priority, which receiver handles a specific ordering, a third-party receiver's manifest/dynamic registration deliverability, an external `setPin` call's permissions, a genuine DS3 PIN, or the internal OEM `.so` plugin loader. Do not infer these from the existence of an OEM receiver.
- **Interpretation:** the earlier public-source `BondStateMachine` pairing broadcast path **has a directly corresponding installed M3 OEM receiver/Activity**. This closes the question "does the M3 have a pairing receiver?" as **YES for the privileged OEM Settings app**, but leaves "can an independent low-privilege plugin get an equivalent callback in time and complete DS3 cable pairing?" **UNRESOLVED**, with native/Java/UHID limitations unchanged.

For an independent app, merely requesting `BLUETOOTH_CONNECT` grants neither `BLUETOOTH_PRIVILEGED` nor authority to change `HidHostService` admission. The OEM TV Settings receiver's privileges must **not** be used as evidence of general third-party app privilege.

**Privacy/security:** No on-device commands run, no PIN/key/address values published, no package dump or OEM binary copied into the repository. Exact original `libbluetooth.so` remains unavailable for new loader disassembly in this session.

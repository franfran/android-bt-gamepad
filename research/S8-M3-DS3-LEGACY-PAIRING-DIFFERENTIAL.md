# S8 — DS3 Legacy Pairing: locate host key/PIN response and distinguish HCI 0x22 from wrong PIN

**Research date:** 2026-10-29. M3 original owner-provided ARM32 `libbluetooth.so` verified SHA256 `4ce119eda2dc211cb38085e8fde3d7ee2fbaaa243df9b20e21636e3c4962bd85`. All ELF inspection offline only; no M3 access, no MAC/PIN/key disclosure. Builds on Draft PRs #38–#40. This is a differential-diagnosis outcome, **not** a working wireless fix.

## Source-grounded actual M3 functions: host key/PIN flow

Mini-debug symbols recovered from **original M3 ELF**:
- `btm_sec_link_key_request(uint8_t*)`, Thumb code VMA **0x25d64c**, size 340.
- `btm_sec_pin_code_request(uint8_t*)`, Thumb code VMA **0x25d7a0**, size 896.
- `btsnd_hcic_link_key_neg_reply` **0x27c83c**.
- `btsnd_hcic_pin_code_req_reply` **0x27c87c**.
- `btsnd_hcic_pin_code_neg_reply` **0x27c922**.
- `btsnd_hcic_link_key_req_reply` **0x27c7b8**.
- `btm_sec_auth_complete` **0x25b5c4**; earlier PR #40 confirms general failure handling for status **0x22**.

**New branch-level proof from original Thumb bytes**:
1. In `btm_sec_link_key_request`, `0x25d72c..0x25d73e` tests a device security-record bit. Depending on this bit, the host either requests a new PIN via **`l2c_pin_code_request` (0x28dee4)**, or selects a stored key via **`btsnd_hcic_link_key_req_reply` (0x27c7b8)**. A separate route at `0x25d76a` calls **`btsnd_hcic_link_key_neg_reply` (0x27c83c)**. The HCI-negative reply is therefore a **real** executable fallback, not evidence that controller hardware rejected authentication.
2. In `btm_sec_pin_code_request`, at `0x25d882..0x25d89c` the native routine fetches **local controller BD_ADDR**, copies it into a 6-byte buffer and compares against the incoming remote address. If the addresses are equal, it takes special handling. Later it selects appropriate PIN response behavior based on pairing state.
3. At `0x25d9c0..0x25d9d2`, the native routine takes a stored PIN length from global `+0x3661`, obtains PIN bytes at `+0x3662`, invokes **`btsnd_hcic_pin_code_req_reply` (0x27c87c)**, and **clears saved PIN length**. Its alternate branch at `0x25d902` invokes `btsnd_hcic_pin_code_neg_reply` (0x27c922). Both replies exist in the original M3 binary.
4. `btm_sec_pin_code_request` contains logic to route PIN-request prompts or device-specific handling, so **HCI PIN Reply command acceptance alone does not establish a correct key or successful pairing**.

## Direct comparison with historical DS3 btsnoop

| Historical observation (private capture) | Most precise conclusion |
|---|---|
| DS3 initiates HID Control PSM `0x11` | Remote peer actively requests Classic L2CAP HID Control |
| Host HCI Authentication Requested `0x0411` | Host initiated controller authentication; command issuance is verified in M3 ELF |
| HCI Link Key Request followed by Negative Reply | Host did not supply a usable existing key in that response; **this does not mean PIN was rejected** |
| HCI PIN Code Request followed by 6-byte PIN Reply | Host responded to controller PIN challenge; correctness/byte order cannot be inferred without comparing the actual locally generated bytes to required protocol representation |
| HCI Authentication Complete **status `0x22`** | **LMP Response Timeout**; not the protocol's distinct `0x05` Authentication Failure nor `0x06` PIN or Key Missing |
| HCI Disconnection Complete reason `0x22` | Terminated after controller-level timeout; alone cannot allocate fault to M3 firmware vs DS3 firmware/radio |

Per Bluetooth Core specification, `0x22` is LMP Response Timeout on BR/EDR: an LMP transaction did not receive valid response in its timeout window, typically specified as **30 seconds**. This is a controller-side LMP-level error report, **not a host-side PIN equality verdict**. A status `0x22` is consistent with (not proof of) firmware interoperability, peer silence, timing or a preceding pairing incompatibility that stalls subsequent LMP exchange.

## DS3-specific comparison and implications

- BlueZ's Sixaxis plugin uses **USB to examine/set master Bluetooth address**, then registers/enrolls the device as a known Bluetooth peer. This validates the ownership relationship, but **does not make default Android 12 pairing behavior automatically compatible**.
- BthPS3 for Windows documents that standard pairing dialog is insufficient and a device-specific Bluetooth profile/filter mechanism is required. However, BthPS3 targets Windows drivers, **not** Android UART HCI. Its PSM restrictions are a Windows-specific constraint and **must not be copied** as proof that the M3 Classic L2CAP PSM registration caused the observed `0x22`.
- This M3 binary already registers HID PSMs 0x11/0x13 and has Classic security / PIN reply handling. The open question is **which actual pairing response bytes and controller timing** satisfy the DS3's LMP procedure; not mere existence of HID service registration.
- A 6-byte HCI PIN length is consistent with the DS3 host-address convention but is insufficient evidence of correct bytes/order. The relevant question is **what was sent**, not just the length. Historical snoop should remain private; a local redacted validator can check local-address representation and packet sequence, without committing MAC or PIN data.

## Prioritized next action (read-only; no further intrusive tests)

1. **Offline capture audit:** If the historical HCI snoop remains accessible privately, extract **only timing deltas** for HCI Link Key Request → negative response, PIN Code Request → PIN Reply, PIN Reply → Authentication Complete, and compare the 6 PIN bytes to the M3's local BD_ADDR in the expected host byte order. Report **match / reverse-order match / neither** and elapsed seconds, **never raw addresses or keys**. The copied static evidence does not contain packet timestamps/PIN payload; therefore this analysis cannot make that determination today.
2. **Failure localization:** Check whether the second observed attempt **lacks PIN reply** because Android supplied no PIN (host gate), versus a first attempt with a reply that still timed out (controller-level step). Keep these attempts separate; aggregate error 0x22 can conceal different failure sequences.
3. If PIN content and timing are correct but LMP still times out, **prioritize controller/DS3 interoperability or timing** over host HID security-policy patches. If content differs, focus on scoped host PIN-byte-order handling first. Only after an explicitly approved recovery/rollback plan should an on-device change be considered.
